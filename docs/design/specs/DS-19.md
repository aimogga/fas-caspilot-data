# DS-19 — Dark mode: an Appearance choice in the account menu, remembered on the device, no flash, every route checked on the dark surface
Source docs: `docs/design/POLISH_PLAN.md` row DS-19 ("Theme toggle in the user menu; `.dark` persisted + `prefers-color-scheme` + no-flash script; dark shots and axe for every route; chart ramp contrast"); `docs/DESIGN.md` Part 1 tokens (the `.dark` block in `app/globals.css` already carries every surface, status, chart and sidebar token) and Part 2 rule 2 (axe clean); `docs/DESIGN_WORKFLOW.md` (AA "in light and dark"); `docs/design/fas-screen-plan-part2.md` §4 board row ("Print: light theme") and the P3 "dark-mode QA" line; `.claude/skills/design-polish/references/*`; precedents DS-13b and DS-17 (print sheets), DS-18b (shell files, spec format).
**Depends on:** DS-18b on main (#277, `ShellFrame` glyphs). **Budget:** ≤ 400 hand-written lines (D-012); whole packet fits in sub-packet a. **Before and after shots:** the supervisor, after merge, with `pnpm shots … --dark` (the shots script adds `.dark` itself, so it works the same before and after this packet).

## Purpose and users
A board member reading the quarterly summary on a phone at night, a case manager whose laptop is set to dark, and an admin who simply prefers it: each should get a calm dark page that keeps every rule of the light one (one accent, tokens only, the hatch for hidden cells, the explain faces readable) and should never see a white flash before the dark page paints. Printing stays light: the board and packet sheets are one ink on white.

| Role | Gets |
|---|---|
| staff, admin, board_viewer | `Appearance` in the account menu with `Light`, `Dark` and `Match device`; the current choice marked; the choice remembered on this device; the page follows the device until a choice is made |
| signed-out visitor (`/login`, `/403`) | the device setting (or the choice stored earlier on this device) applied before paint; no menu, because there is no account menu |

## Scope (sub-packet a = the whole packet)
- `lib/shell/theme.ts` (pure): `THEME_KEY` (`fas-theme`), `THEME_OPTIONS`, `parseTheme`, `serialiseTheme`, `resolveTheme(choice, systemPrefersDark)`, `applyTheme(root, resolved)` (`.dark` class + `color-scheme`), `THEME_BOOT_SCRIPT` (three lines, no dependencies, wrapped in `try`).
- `app/layout.tsx`: the boot script inline in `<head>`; `suppressHydrationWarning` on `<html>` because the script changes the root's class and style before React hydrates.
- `components/shell/ThemeMenu.tsx` (client): a `role="group"` labelled `Appearance` with three `aria-pressed` buttons; the stored choice read through `useSyncExternalStore` (server snapshot `Match device`, so hydration never disagrees); listeners on `prefers-color-scheme` (Match device follows the device live), on `matchMedia("print")` and `beforeprint`/`afterprint` (a dark page prints light and returns to dark afterwards).
- `components/shell/ShellFrame.tsx`: `<ThemeMenu />` between the role line and `Sign out` in the `details` menu.
- `components/ui/button.tsx`: the destructive variant drops `text-white` and the `dark:bg-destructive/60` override for `text-destructive-foreground` on the token pair, which already carries a dark value with the right contrast.
- Dark audit of the charts, map and trust faces (table below): everything already reads from tokens, so no fill or stroke changes.
- Out of scope: a theme control on `/login` (no account menu there; the device setting applies), a server-side cookie (the choice is a device preference, not account data), a per-role default.

### First impression (critique)
Today the `.dark` tokens exist but nothing applies them: no menu, no `prefers-color-scheme` hook, so `tests/e2e/map.spec.ts`'s "dark" pass has been a second light pass. Rendered in dark by hand, the pages hold up: warm charcoal surfaces, the one green accent lifted for contrast, the serif headlines intact. Two faults: the destructive button paints white text on a light red (about 2.5:1) and `color-scheme` is never set, so scrollbars and native selects stay light in a dark page.

## Decisions
1. `aria-pressed` buttons rather than a radiogroup: each row is its own tab stop, no arrow-key script, the pressed state is announced, and the tick makes it visible.
2. The stored value is `light` or `dark` only; Match device removes the key, so a device with no key starts from its own setting (no migration if the default ever changes).
3. Print stays light by script (`matchMedia("print")` + `beforeprint`) rather than CSS: undoing the `.dark` tokens in `@media print` would mean restating every value, and `app/globals.css` is kit-only.
4. `color-scheme` is set as an inline style on `<html>` by the same code that sets the class, so the two can never disagree.
5. `tests/e2e/map.spec.ts`'s existing light/dark loop is left as is: with this packet its dark pass becomes a real one.
6. The gallery `/ui` was the local proof for the chart and trust faces (no Supabase in this shell): axe clean at 375 and 1024 in dark, screenshots reviewed.
